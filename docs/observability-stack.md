# Стек наблюдаемости

## Выбранный стек

В проекте используется составной стек наблюдаемости:

- инструментирование `OpenTelemetry` внутри Go-сервисов
- `Jaeger` для распределенных трейсов
- `Prometheus` для сбора метрик
- `Alertmanager` для маршрутизации алертов
- `Grafana` для дашбордов
- `Loki + Promtail` для централизованных логов

## Почему выбран именно этот стек

Этот стек был выбран потому, что он четко разделяет три основных сигнала наблюдаемости:

- трейсы обрабатывает `Jaeger`
- метрики и алерты обрабатывают `Prometheus + Alertmanager`
- логи собирают `Loki + Promtail`
- `Grafana` дает единый интерфейс для просмотра метрик, трейсов и логов

Для проекта такой разделенный стек проще объяснять и проверять, чем более тяжелую универсальную all-in-one платформу. Он хорошо подходит для локальной Docker-разработки и делает каждый сигнал явным архитектурным компонентом.

## Сравнение с другими вариантами

### SigNoz

`SigNoz` — сильная all-in-one платформа наблюдаемости на базе `OpenTelemetry`, которая объединяет трейсы, метрики, логи, дашборды и алерты. Это хороший продуктовый вариант, но для нашего проекта мы выбрали более явный стек, где каждый компонент виден отдельно и проще соотносится с требованиями отчета.

### Jaeger

`Jaeger` сфокусирован на распределенном трассировании. Мы используем его именно в этой роли, а не пытаемся закрыть им всю поверхность наблюдаемости.

### NetData

`NetData` хорошо подходит для инфраструктурного мониторинга в реальном времени и быстрого обнаружения аномалий. Для нашего проекта он менее естественен как главный центр наблюдаемости, потому что нам важны явные прикладные трейсы и Prometheus-style алерты вокруг собственных микросервисов.

### Coroot

`Coroot` — современная full-stack платформа наблюдаемости с сильной `eBPF`-составляющей и высокой степенью автоматизации. Это интересный вариант, но для нашего проекта он добавил бы больше платформенной сложности, чем нужно. Мы выбрали более прозрачный стек, который проще защищать по шагам.

## Что уже наблюдается

- HTTP-метрики каждого сервиса через `/metrics`
- распределенные трейсы для входящих HTTP-запросов и межсервисных HTTP-вызовов
- централизованные контейнерные логи через `Loki/Promtail`
- базовые правила алертов для:
  - недоступности сервиса
  - повышенного процента `5xx`
  - высокого `p95` по задержке
